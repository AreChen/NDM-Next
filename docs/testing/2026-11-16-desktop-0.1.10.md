# Desktop 0.1.10 verification

Source: `c920f2871056e118771504d6504c3c9829d7b783`, tag `desktop-v0.1.10`.

## Windows diagnosis

- The installed app was still 0.1.8. Its cached 0.1.9 installer matched the published file: **29,108,383 bytes**, SHA-256 `bd326af4391e937d2b43e05d2ec46e590113a4b8e55d4a22ebb07fa1c0b49935`. The observed failure was therefore not an incomplete copy of that cached installer.
- Read-only IPC inspection found the app alive with its readiness event cleared after shutdown had been requested. The previous Windows shutdown listener accepted only one notification. A repeated-request regression failed against that implementation and passed with the persistent listener.
- The update flow now waits for the real installer guard, then quits the desktop app. It does not wait inside the old app for the installer to finish. The GUI quit command no longer depends on the initiating view remaining usable.
- This establishes defects in shutdown/retry handling; it does not identify every failure that the previous generic update error could hide. API, download, storage, integrity, launch and installer failures now have separate messages and available status codes.

## Local verification

- Rust **1.100.0**, Windows workspace: **218 passed**, zero failures. Opt-in network, media and subprocess fixtures remain excluded from the default run.
- All-target workspace Clippy with warnings denied, Rust formatting and Git whitespace checks passed.
- Updater regressions cover concurrent ranges, intermediate progress, cache reuse, digest/length failures, untrusted redirects, installer handoff, early installer failure and repeated shutdown requests.
- A public-network smoke test downloaded the actual 0.1.9 GitHub installer through the new production updater using **16 segments**, then verified its exact length and SHA-256. It never executed the installer.
- The isolated NSIS integration suite, including its timeout scenario, passed using the host extracted from the genuine 0.1.9 release. It covers graceful closure, replacement, relaunch, existing data preservation and refusal to overwrite an app that does not exit. Production installer scripts are unchanged in this patch.
- Update staging cleanup tests cover owned directories, active-update leases, expiry and macOS DMG filename ownership.

The user's installed application and profile were not replaced. Native app/browser UI review was left to the user. An older app that has already failed during shutdown may need one manual upgrade after exiting it fully; the running old binary cannot acquire the new updater until replaced.

## Live exit investigation

The user subsequently reported that the installed 0.1.8 app would not quit. A noninvasive WinDbg inspection found its main thread waiting normally in `GetMessageW`; Tokio workers were mostly parked. Its main window still existed but was hidden. SQLite contained no running or queued downloads. The shutdown event was set and unconsumed, with only the wake/show IPC waiters remaining. This corroborates the stopped one-shot shutdown listener rather than a blocked download worker.

The old GUI command loop also stopped on a failed Show/Refresh window lookup and ignored errors from its window-dependent Quit invocation. These are confirmed source defects already addressed in the tagged patch; the old binary did not retain logs identifying which window lookup first failed.

After checking the exact process image and main thread, a standard `WM_QUIT` message—the mechanism used by GPUI's Windows platform—allowed the original process to exit. No forced process termination was used. A subsequent short-lived instance also exited; a final check found no desktop or host processes. Completed task count was unchanged and SQLite `quick_check` returned `ok`. Four uncommitted browser preparations were marked failed by the old app's startup recovery, without starting those downloads.
